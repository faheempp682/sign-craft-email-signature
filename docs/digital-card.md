# Digital card

A public landing page per person at `/c/<slug>`: photo, name, title, company, bio, tap-to-call, tap-to-email, website, social buttons, booking link, **Save contact** (vCard) and a QR code of the card's own address. Owners manage cards at `/cards` (needs the `digital_card` feature). Migration: `supabase/migrations/0007_digital_cards.sql`.

## Privacy model

**Private by default.** A new card is unpublished and `noindex`.

**What is public once published:** exactly what the preview shows: name, title, company, bio, photo, phone, email, website, address, social links, booking link, accent colour. Anyone with the link can read it, download the vCard and scan the QR. Do not enter anything you would not put on a business card.

**What is never public:** the owner id, the organization, timestamps, your account email (unless you typed the same address as the card email), your other cards, whether an unpublished card exists.

How it is enforced:
- Anonymous visitors have **no** privileges on the table. They can only call `public.get_public_card(slug)` (security definer, fixed `search_path`), which returns the public columns of a *published* card and nothing else. The public pages call only that function, without cookies.
- A missing card and an unpublished card both return the same 404 page (and the vCard/QR routes the same 404 text), so nothing is revealed about private cards.
- Owners read and write only their own rows (RLS). `owner_id` and `created_at` cannot be updated (no transfers). A card can only be attached to an organization the owner belongs to. Admins can read and delete any card (moderation) but not edit.
- Search engines: pages send `noindex, nofollow` unless the owner turns on **Allow search engines**.
- Every link is sanitised twice (database CHECKs and `lib/cards/links.ts`) to https, `mailto:` or `tel:`. A value that fails is left out of the page.

**Unpublishing:** open the card at `/cards/<id>` and switch **Published** off (immediate, takes effect in the database at once), or delete the card. The page, vCard and QR then answer 404. Caches: the vCard is cached for up to 60 seconds and the QR for up to an hour (the QR only encodes the address, no personal data). If a card must disappear everywhere right away, delete it. Deleting an account deletes its cards.

If an admin switches the `digital_card` feature off for someone, their **already published cards stay public** until they (or an admin, by deleting) unpublish them. The flag gates the owner screens and API, not visitors.

## vCard

`GET /c/<slug>/vcard` returns vCard 3.0 (RFC 2426), `Content-Type: text/vcard; charset=utf-8`, `Content-Disposition: attachment; filename="<slug>.vcf"` (the filename is reduced to `a-z 0-9 -`).
- CRLF line endings, folded at 75 octets on UTF-8 character boundaries.
- Text values escape `\`, `;`, `,` and newlines (as `\n`); other control characters are removed, so a field value cannot start a new property (no CRLF injection).
- Fields: N, FN, ORG, TITLE, TEL, EMAIL, URL (website, the card's own address, booking), ADR (free text in the street part), NOTE (bio), PHOTO (https URI), X-SOCIALPROFILE (one per social link).

## QR code

`GET /c/<slug>/qr` returns an SVG of the card address (`?format=png&size=512` for a PNG, size 128 to 1024, `&download=1` to force a download). Error correction M, 2-module quiet zone, generated by the `qrcode` package. The address is `NEXT_PUBLIC_SITE_URL` when set, otherwise the request host. **Set `NEXT_PUBLIC_SITE_URL` in production** so QR codes and vCards always carry your real domain. The editor makes its own copy of the QR in the browser (so it works before publishing); the PNG download is 1024 px.

## Limits

- 5 cards per person (enforced by a database trigger, serialised per owner).
- Slug: 3 to 40 characters, lowercase letters, digits, hyphens, starting and ending with a letter or digit, unique, reserved words blocked (admin, api, login, c, b, r, vcard, qr, and more; list in the migration and `lib/cards/schema.ts`).
- Name 100, title 100, company 100, bio 300, address 200, URLs 500, phone 30, email 200; up to 10 social links from the same networks as signatures.
- Public vCard route: 30 requests per minute per client address; QR route: 60 per minute. This is an in-memory limiter per server instance; on several instances or serverless, add an edge/CDN rate limit as well. The page itself is not rate limited (it is one cheap database function call).

## For the integrator

- `lib/cards/signature-link.ts`: `cardUrl(slug, origin)` returns `https://host/c/<slug>` or `null`; `signatureCardLink(slug, origin, label?)` returns `{ href, label }` for "add my card link to my signature". Use the app's public origin, and only offer it for published cards (`GET /api/cards` lists the owner's cards with `published`).
- Nav link: `/cards` for people with the `digital_card` feature.
- API: `GET/POST /api/cards`, `PUT/PATCH/DELETE /api/cards/<id>`, `GET /api/cards/slug?slug=&except=`. All need `digital_card`; writes check origin.

## Not verified against real services

The migration is tested in PGlite, not on a hosted Supabase project, and the public page was checked with fake data (it needs migration 0007 applied and real Supabase variables to serve a real card). Verify: apply 0007, enable `digital_card` for yourself, create and publish a card, open `/c/<slug>` in a private window, scan the QR with a phone, tap Save contact on iOS and Android, unpublish and confirm the 404.
